# План MILEAGE: пробег больше 400 000 км → решение review

- Задача: `MILEAGE` (день 1, ДЗ.1) · Дата плана: 2026-09-24 · Сверка со спекой: 2026-09-27
- Правило: «пробег авто не больше 400 000 км, иначе решение review»; порог из `backend/config/rules.php`, не хардкод
- Источник требований после сверки: `docs/spec/spec_MILEAGE.md` (v0) — план приведён в соответствие со спекой; спека приоритетнее плана при расхождениях

## Что изменилось при сверке со спекой (сводка расхождений)

1. **Неизвестный пробег (REQ-MILEAGE-04).** План требовал 422 для отсутствующего / `null` / `''` mileage. Спека: все три формы «неизвестно» проходят валидацию без 422 и получают `review` (AC-MILEAGE-05 — AC-MILEAGE-07). Старый шаг 6 (ужесточение валидатора) заменён на противоположный — валидатор обязан пропускать неизвестный пробег.
2. **Приоритет review над reject (REQ-MILEAGE-03).** Вопрос 1 старого плана закрыт спекой: `review` по пробегу перекрывает любой исход по LTV, включая `reject` при LTV > 85 % (AC-MILEAGE-04). Тест больше не «спорен», а обязателен.
3. **Причина review в ответе API (REQ-MILEAGE-06).** Старый план выводил причину review в «не входит». Спека требует непустую причину в `POST /api/ltv` и `POST /api/applications` при любом `review` — и по пробегу, и по LTV (AC-MILEAGE-10 — AC-MILEAGE-13). В план добавлены контроллеры, которых старый план не трогал.
4. **Открытые вопросы.** Старые вопросы 1, 3, 4, 5 закрыты спекой; вопрос 2 стал OQ-MILEAGE-01 (граница 500 000 — открыта для руководства, в реализации не трогаем). Обнаружен новый OQ-MILEAGE-02: сохранение заявки без пробега через `POST /api/applications` (см. Риски).

## Как считается решение сейчас

- `ApplicationValidator::validate()` (строки 43–46): `mileage` обязателен, диапазон `0..max_mileage_km` (500 000, `rules.php:23`). Отсутствие или `null` → `-1` → `ValidationException` (422). Латентное поведение: пустая строка `''` приводится к `0` и молча проходит как «0 км».
- `AssessmentService::assess()`: валидация → `LtvCalculator` → `DecisionEngine::decide(float $ltv)` → `approved_limit` (approve = запрошенная сумма, иначе 0, `AssessmentService.php:39`).
- `DecisionEngine` знает только LTV; валидационная зона review — 60.0 < LTV ≤ 85.0 (`rules.php:44–45`).
- Хранение: `vehicles.mileage_km INT UNSIGNED NOT NULL` (`schema.sql:22`), `decisions.decision ENUM('approve','review','reject')` — ENUM уже готов к review, менять не нужно.
- Диапазон 400 001–500 000 сегодня проходит валидацию и получает решение чисто по LTV — именно это меняет задача. Пробег 500 001+ остаётся 422 (OQ-MILEAGE-01, спека «Не входит» п. 4).

## 2. Шаги

1. **rules.php** — добавить `'review_above_mileage_km' => 400000` рядом с `max_mileage_km` (500 000) с комментарием: `max_mileage_km` — граница валидации (выше → 422), новый ключ — граница решения (выше → review).
2. **MileageRule.php** — новый `final` класс, сигнатура:
   ```php
   final class MileageRule
   {
       public function __construct(private readonly int $reviewAboveKm) {}
       /** true, если пробег известен и строго больше порога */
       public function requiresReview(int $mileage): bool;
   }
   ```
   Неизвестный пробег (`null`) правилом не обрабатывается — им занимается `AssessmentService`: у него другая причина review.
3. **MileageRuleTest.php** — закрыть границы из раздела «Тесты», прогнать `make test`.
4. **ApplicationValidator.php** — блок mileage (строки 43–46) заменить на:
   - `raw = payload['mileage'] ?? null`; `raw === null || raw === ''` → `mileage = null`, без ошибки;
   - нечисловое (например `'abc'`) → ошибка `mileage` («Пробег должен быть числом»);
   - иначе `(int) $raw` и проверка `0..max_mileage_km` как сейчас.
   Тип возврата: `mileage` становится `int|null` — обновить docblock `validate()`. Существующие тесты, где mileage присутствует числом, не задеты.
5. **AssessmentService.php + AppFactory.php** — прокинуть `MileageRule` в конструктор; в `assess()` после `decide()`:
   - `mileage === null` → `decision = REVIEW`, причина «Пробег неизвестен»;
   - `mileage !== null && requiresReview(mileage)` → `decision = REVIEW` (замещает любой исход LTV, включая reject), причина вида «Пробег больше 400 000 км» (число из `MileageRule`, не хардкод);
   - решение по LTV — `review` → причина «LTV …% — требуется ручная проверка» (порог из `DecisionEngine`, не хардкод);
   - `approve` / `reject` → причина пустая (`null` или `''`, поле в ответе опционально);
   - `approved_limit` при review остаётся 0 по существующей строке 39; при неизвестном пробеге LTV всё равно считается (запрошенная сумма и market_value обязательны) и попадает в ответ.
   Тексты причин — синтетические, формулируются в `AssessmentService`; спека тексты не задаёт, требует лишь непустоту при review.
6. **ApplicationController.php** — добавить `decision_reason` в ответы `ltv()` и `create()`; статус-коды (200/201/422) не меняются.
7. **Тесты сервисного и HTTP-уровня** — сценарии из раздела «Тесты», полный прогон `make test` + `make lint`.

Порядок выбран так, чтобы каждый шаг закрывался тестами до перехода к следующему.

## 4. Риски

- **OQ-MILEAGE-02 — сохранение заявки без пробега (главный блокер).** `POST /api/applications` отвечает после записи в БД, а `vehicles.mileage_km INT UNSIGNED NOT NULL` не хранит «неизвестно». REQ-MILEAGE-04 требует не-422 на этом пути, intent одновременно запрещает миграции — два решения intent конфликтуют. Пока OQ не закрыт: валидация и `assess()` пропускают неизвестный пробег (иначе /api/ltv не выполнить), но `POST /api/applications` с неизвестным пробегом упадёт на INSERT (500). Спека сознательно не включила AC на этот путь — план тоже; путь помечен как заблокированный OQ-MILEAGE-02. Без ответа человека не выбирать плейсхолдер (например 0) и не делать миграцию самовольно.
- **OQ-MILEAGE-01 — две границы.** 400 000 (решение) и 500 000 (валидация) образуют окно 400 001–500 000 → review; 500 001+ → 422. Спека подтвердила это как позицию по умолчанию, вопрос выравнивания открыт для руководства. Границы легко перепутать при поддержке.
- **Смягчение валидатора (шаг 4).** Отсутствие / `null` / `''` в mileage раньше давали 422 (или молча 0 км) — теперь проходят с review. Меняется контракт API: клиенты, полагавшиеся на 422 при пустом пробеге, получат 200 со статусом review. Фронтенд (поле `required`) не затронут.
- **Причина review — расширение ответа.** Новое поле `decision_reason` в обоих эндпоинтах. Строгие ассерты существующих тестов на форму ответа могут сломаться — проверить перед прогоном; статус-коды не меняются.
- **approved_limit.** Заявок с review станет больше, у всех лимит 0 — операторы увидят больше нулевых лимитов; логика не меняется, меняется распределение решений.
- **Хранение известных пробегов.** `mileage_km INT UNSIGNED` вмещает 400 001; ENUM `decisions.decision` уже содержит `review` — миграций не требуется.
- **Существующие тесты.** Payload-хелперы используют 96 000 / 84 000 км — границы не задеты; после шагов 4–6 обязателен полный `make test`.

Не входит (вне объёма задачи, по спеке):

- пересчёт решений по ранее сохранённым заявкам (REQ-MILEAGE-07);
- миграции БД (кроме заблокированного OQ-MILEAGE-02);
- правки frontend;
- изменение валидационной границы `max_mileage_km = 500000` (OQ-MILEAGE-01);
- сверка пробега с внешним справочником по VIN, детекция «клиент называет меньше» (материал `docs/sources/CASE-08.md`, `client_note.md`);
- скидки за пробег и возраст в оценке залоговой стоимости;
- LOAN-12 — лимит суммы по `ltv_by_age`.

## Вопросы, открытые после сверки со спекой

Спека закрыла старые вопросы 1 (review перекрывает reject), 3 (неизвестно → review, не 422), 4 (причину включить) и 5 (только новые заявки). Остались открытыми только её собственные OQ:

1. **OQ-MILEAGE-01.** Оставить `max_mileage_km = 500000` (окно 400 001–500 000 → review, 500 001+ → 422) или выровнять границу с порогом 400 000? До ответа — не менять; план реализует позицию по умолчанию.
2. **OQ-MILEAGE-02.** Как сохранять заявку без пробега через `POST /api/applications`: миграция колонки (снимает «без миграций»), значение-плейсхолдер (смешивает «неизвестно» с числом) или иное? Блокирует AC на этом пути; `/api/ltv` реализуется полностью.

Чего не хватает для полной реализации: ответа руководства по OQ-MILEAGE-02 (способ хранения неизвестного пробега при сохранении) — остальное покрывается спекой без додумывания.
