# Спека MILEAGE: пробег больше 400 000 км → решение review

- Задача: `MILEAGE` (день 1, ДЗ.1) · Дата спеки: 2026-09-27 · Статус: v0 — до ответа руководства по OQ-MILEAGE-01
- Единственный источник требований: `docs/intent/intent_MILEAGE.md` (Grill Me, 2026-09-27). Всё ниже либо трассируется на него, либо явно помечено как обнаруженное при сверке кода (OQ-MILEAGE-02 — вопрос, не требование).
- Сверка фактов кода: `docs/setup/code_map.md`, `docs/plan/plan_MILEAGE.md`, `backend/config/rules.php`, `backend/src/Domain/DecisionEngine.php`, `backend/src/Domain/ApplicationValidator.php`, `backend/src/Domain/AssessmentService.php`, `backend/src/Http/ApplicationController.php`, `backend/src/Repository/ApplicationRepository.php`, `db/schema.sql`.
- Ссылки в тексте: `intent:N` — строка N файла intent; `план:N` — строка N `docs/plan/plan_MILEAGE.md`; `README:N` — `docs/spec/README.md`; код — `файл:N`.
- Формат: `docs/spec/README.md` — атомарные REQ, AC в Given/When/Then, AC на границе каждого числового правила, у каждого числа источник.

## Входит / не входит

### Входит

1. Правило пробега в расчёте решения: известный пробег 400 001 км и больше → `review`; 400 000 км включительно — допустимо, решение не меняется. [intent: 3, 9, 58]
2. Приоритет правила: `review` по пробегу перекрывает любое решение по LTV, включая `reject` при LTV больше 85 %. [intent: 18–20, 50]
3. Неизвестный пробег — поле `mileage` отсутствует, равно `null` или пустой строке `''` — заявка проходит валидацию (без 422) и получает `review`. [intent: 24, 26–28, 51]
4. Причина review в ответах `POST /api/ltv` и `POST /api/applications` при решении `review`; контракт API и тесты расширяются. [intent: 42–44, 52]
5. Порог 400 000 — отдельный ключ в `backend/config/rules.php` (пример имени — `review_above_mileage_km`), не хардкод в коде. [intent: 10, 58]
6. Правило действует только при расчёте решения новой заявки. [intent: 12, 58]

### Не входит

1. Пересчёт решений по ранее сохранённым заявкам. [intent: 12, 58]
2. Миграции БД. [intent: 12, 58] — пересекается с REQ-MILEAGE-04 на пути сохранения заявки без пробега, см. OQ-MILEAGE-02.
3. Правки frontend. [intent: 12, 58]
4. Изменение валидационной границы `max_mileage_km => 500000` (`rules.php:23`): пробег 500 001 км и выше по-прежнему даёт 422, окно 400 001–500 000 даёт `review`. Выравнивание границы с порогом 400 000 — открытый вопрос руководства (OQ-MILEAGE-01), в спеке не решается. [intent: 34–36, 56]

Существующее поведение, которое MILEAGE не трогает: валидация пробега 0–500 000 км (`rules.php:23`), пороги LTV (`rules.php:44–45`), `approved_limit` (запрошенная сумма при `approve`, иначе 0 — `AssessmentService.php:39`), сохранение заявки и решения в БД (`ApplicationRepository.php:22–61`).

## Требования

### REQ-MILEAGE-01 — пробег в пределах порога не меняет решение

Если пробег заявки известен и не больше 400 000 км, решение заявки определяется только действующими правилами LTV (`approve` / `review` / `reject`); правило пробега его не меняет.

- Проверяемость: решение совпадает с расчётом по LTV при пробеге 399 999 и 400 000 км (AC-MILEAGE-01, AC-MILEAGE-02).
- Источник: intent: 3 («пробег авто не больше 400 000 км»), intent: 9 («400 000 — ок, 400 001 → review»), intent: 58.

### REQ-MILEAGE-02 — пробег выше порога даёт review

Если пробег заявки известен и больше 400 000 км (400 001 км и больше), заявка, прошедшая валидацию, получает решение `review`.

- Проверяемость: `decision` в ответе API при пробеге 400 001 км (AC-MILEAGE-03, AC-MILEAGE-10, AC-MILEAGE-11).
- Источник: intent: 3, 9, 50 (итог п. 1).
- «Прошедшая валидацию»: пробег 500 001+ сейчас не доходит до решения (422, `rules.php:23`); до ответа по OQ-MILEAGE-01 правило фактически действует в окне 400 001–500 000 [intent: 56].

### REQ-MILEAGE-03 — review перекрывает reject

При пробеге 400 001 км и больше и LTV больше 85 % (зона `reject` по LTV) итоговое решение — `review`, не `reject`.

- Проверяемость: сценарий «400 001 км при LTV 95 %» (AC-MILEAGE-04).
- Источник: intent: 18–20 (Вопрос 1: «review перекрывает reject»), intent: 50 (итог п. 1); зона reject — `rules.php:45` (`review_max` 85.0), intent: 14.

### REQ-MILEAGE-04 — неизвестный пробег даёт review, не 422

Если пробег неизвестен — поле `mileage` отсутствует, равно `null` или пустой строке `''`, — заявка не отклоняется валидацией и получает решение `review`. Существующее поведение меняется: сейчас отсутствие и `null` дают 422, а `''` превращается в 0 км и проходит (план: 14).

- Проверяемость: ответ без 422 с `decision = review` для каждой из трёх форм «неизвестно» (AC-MILEAGE-05 — AC-MILEAGE-07).
- Источник: intent: 24, 26–28 (Вопрос 2: «неизвестно → review»), intent: 51 (итог п. 2).

### REQ-MILEAGE-05 — порог в конфиге, не хардкод

Значение порога 400 000 задаётся в `backend/config/rules.php` отдельным ключом решения (пример имени — `review_above_mileage_km`), отдельно от валидационного `max_mileage_km`; в PHP-коде (`backend/src/`) порог числовым литералом не встречается.

- Проверяемость: наличие ключа в конфиге и отсутствие литерала 400000 в `backend/src/` (AC-MILEAGE-08, AC-MILEAGE-09).
- Источник: intent: 10, 58.

### REQ-MILEAGE-06 — причина review в ответе API

Если решение заявки — `review`, ответы `POST /api/ltv` и `POST /api/applications` содержат непустую причину этого решения.

- Проверяемость: поле причины в ответах обоих эндпоинтов при review по пробегу и при review по LTV (AC-MILEAGE-10 — AC-MILEAGE-13).
- Источник: intent: 42–44 (Вопрос 4: «включить»), intent: 52 (итог п. 3).

### REQ-MILEAGE-07 — правило только на новые заявки

Правило применяется при расчёте решения новой заявки; ранее сохранённые решения не пересчитываются.

- Проверяемость: заявка, сохранённая до внедрения правила, читается с прежним решением (AC-MILEAGE-14).
- Источник: intent: 12, 58.

### OQ-MILEAGE-01 — граница 500 000 (перенесён из intent, Вопрос 3)

Вопрос: оставить `max_mileage_km => 500000` (окно 400 001–500 000 → `review`, 500 001+ → 422 — позиция по умолчанию) или выровнять границу с порогом 400 000 (любой пробег выше → `review`)? [intent: 34–36, 56]

Статус: перенесён — остаётся открытым пунктом для руководства. До решения действует позиция по умолчанию из intent: граница 500 000 не меняется («Не входит», п. 4). REQ-MILEAGE-02 сформулирован через «прошедшую валидацию» и верен при любом исходе; после ответа — правка этой спеки.

### OQ-MILEAGE-02 — хранение заявки без пробега (новый, обнаружен при сверке кода; в intent отсутствует)

REQ-MILEAGE-04 требует пропускать заявку с неизвестным пробегом без 422. Для `POST /api/ltv` путь целиком лежит в расчёте. Но `POST /api/applications` отвечает после сохранения (`ApplicationController.php:34`), а колонка `vehicles.mileage_km INT UNSIGNED NOT NULL` (`schema.sql:22`) не может хранить «неизвестно». При этом intent фиксирует одновременно «не 422» (intent: 51) и «миграции БД не нужны» (intent: 12, 58) — на этом пути два решения intent конфликтуют и без человека вместе нереализуемы: нужна либо миграция (снимает «без миграций»), либо значение-плейсхолдер (смешивает «неизвестно» с числом), либо иное решение.

Статус: перенесён человеку; в спеке не решается, требований о способе хранения не добавлено. AC на сохранение заявки без пробега через `POST /api/applications` не включён до ответа; требования REQ-MILEAGE-04 и REQ-MILEAGE-06 на этот путь распространяются в полном объёме.
