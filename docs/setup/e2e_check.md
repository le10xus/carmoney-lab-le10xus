# E2E-проверка через UI (Playwright)

Дата проверки: 2026-10-19. Окружение: браузер открыт через Playwright, сервис
carmoney-lab поднят через `docker compose up -d` (образ `carmoney-lab-backend`,
MySQL 8 в соседнем контейнере; пересборка не выполнялась — ранее `make up`
падал на стадии `apt-get install unzip git` из-за недоступности apt-репозиториев).
Health-check `GET /health` вернул `200 {"status":"ok","service":"carmoney-lab"}`.

Перед проверкой установил, к каким полям относятся числа `400001` и `600000`:
в `backend/config/rules.php` пробег свыше `review_above_mileage_km = 400000`
даёт решение `review`, а пробег свыше валидационной границы
`max_mileage_km = 500000` — ошибку 422. Поэтому оба числа вводил в поле
«Пробег, км» (mileage), остальные поля формы оставлял дефолтными.

Все остальные поля формы оставлены дефолтными, как их отдаёт страница:
applicant_ref=`CL-0025`, vin=`XTA21099998765432`, year=`2019`, mileage менял,
market_value=`900000`, requested_amount=`450000`, term_months=`24`.

## Случай 1 — пробег 400001 → ожидался `review`

Шаги и что показала система (дословно со страницы):

1. Открыл `http://localhost:8080/`. Заголовок страницы:
   «Предварительная оценка заявки — carmoney-lab». Заголовок h1:
   «Предварительная оценка заявки на заём под ПТС». Под ним примечание:
   «Учебный сервис. Все данные синтетические, реальные заявки сюда вводить
   нельзя.»
2. В поле «Пробег, км» ввёл `400001` (остальные поля не трогал).
3. Нажал кнопку «Отправить заявку».
4. На странице появился блок «Решение» с такими значениями:
   - Решение: `review`
   - LTV: `50 %`
   - Возраст авто: `7 лет`
   - Одобренный лимит: `0 ₽`
   - Номер заявки: `26`

Скриншот: `docs/setup/e2e_400001_review.png`.

Совпало с ожиданием: `decision=review` для mileage=400001.

Параллельная проверка API для тех же данных
`POST /api/applications` с mileage=400001 дала ответ
`{"id":25,"vehicle_age":7,"ltv":50.0,"decision":"review","approved_limit":0,"decision_reason":"Пробег больше 400000 км"}`
(заявка 25 через API; UI показал 26 — вероятно, инкремент счётчика за время
между двумя curl-вызовами и кликом в браузере).

## Случай 2 — пробег 600000 → ожидалась ошибка

Шаги и что показала система (дословно со страницы):

1. На той же открытой странице в поле «Пробег, км» заменил значение
   на `600000`.
2. Нажал кнопку «Отправить заявку».
3. На странице появился блок «Заявка не принята» с единственным пунктом
   списка: `mileage: Пробег от 0 до 500000 км`. Блок «Решение» при этом не
   отображается.

Скриншот: `docs/setup/e2e_600000_error.png`.

Совпало с ожиданием: заявка отклонена по валидации mileage.

Параллельная проверка API для тех же данных
`POST /api/applications` с mileage=600000 вернула
HTTP 422 и тело `{"errors":{"mileage":"Пробег от 0 до 500000 км"}}` — текст
тот же, что вывел UI.

## Что не удалось / не делалось

- Пересборка образа backend через `make up` упала на стадии
  `apt-get install unzip git`: Docker Desktop запустил daemon только после
  `open -a Docker`, но apt-репозитории в build-контексте недоступны, поэтому
  поднял существующий образ через `docker compose up -d` (без `--build`).
  Этот шаг зафиксирован, чтобы было видно, как именно сервис оказался живой.
- В консоли браузера Playwright при первом открытии страницы было 1 сообщение
  уровня error, после второго клика — 2 (логи лежат в
  `.playwright-mcp/console-2026-10-19T15-32-20-298Z.log`); на UI-поведение
  это не повлияло, причину не расследовал — задача была проверить два
  сценария mileage.
- Скриншоты сделаны в масштабе `css`, `fullPage: true`. Дальнейших действий
  (коммит, отправка в репозиторий) не выполнял.
